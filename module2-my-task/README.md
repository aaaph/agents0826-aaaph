Агент над реєстром прогонів і логами. Реалізує agentic loop у патерні ReAct:
спостерігає → міркує → діє → знову спостерігає, доки не дійде до відповіді
або чесно не скаже, що її немає.

Каркас — `module1` з репозиторію курсу (`core/agent.py`, `core/escalation.py`,
`run.py`, `cost.py` без змін). Свій домен — уся тека `domain/` і `data/`.

## Бізнес-кейс

**Користувач:** Perception інженер. У команди нічний прогін бенчмарків: кілька алгоритмів × кілька конфігів × кілька сиквенсів. Вранці треба зрозуміти, що вночі зламалось.

**Ключова теза:** він приходить із **симптомом, а не із запитом**. «Щось просіло
після вчорашнього мерджа», «нічний джоб не дав метрик», «а інерціалка взагалі
щось дає?». Він не знає `run_id`, часто не знає навіть, який прогін дивитись.

Саме тому тут агент, а не дашборд. Перевірка проста: якщо питання завжди одне й
те саме — потрібен дашборд. Агент виправдовує себе там, де **маршрут щоразу
інший**. У цьому домені він справді інший — три різні входи в одні й ті самі дані:

| з чим приходить інженер         | вхід              | далі                               |
| ------------------------------- | ----------------- | ---------------------------------- |
| симптом — «зривався трекінг»    | `search_logs`     | → `get_run` → `get_metrics`        |
| гіпотеза — «ORB-SLAM3 на EuRoC» | `find_runs`       | → віяло `get_metrics` / `scan_log` |
| ключ — «run-0141»               | одразу `scan_log` | —                                  |

## Каскад: bronze → silver → gold

| шар                              | де живе                     | інструмент                              |
| -------------------------------- | --------------------------- | --------------------------------------- |
| **bronze** — сирі події          | `data/logs/run-XXXX.log`    | `search_logs` шукає подію по всіх логах |
| **silver** — агрегація на льоту  | рахується з bronze на запит | `scan_log` — кадри, фічі, кейфрейми     |
| **gold** — попередньо пораховане | `RUNS[rid]["ate"]`          | `get_metrics`                           |

Правило, за яким поділено шари: **попередньо рахуй те, чого не вивести; виводь
те, що виводиться.** ATE потребує еталонної траєкторії, якої в лозі немає — тому
вона лежить готовою. Момент зриву трекінгу в лозі є — тому його рахує `scan_log`.

## Дані

Зерно: **один запис = одне виконання алгоритму на одному сиквенсі**. Метрики й лог
належать саме йому, тож жоден рівень каскаду не змішує масштаби. 12 виконань,
11 логів по 58–86 рядків (кадр = секунда).

| виконання              | сценарій                                                        |
| ---------------------- | --------------------------------------------------------------- |
| `run-0141`…`run-0143`  | ORB-SLAM3 stereo-inertial на EuRoC                              |
| `run-0144`…`run-0146`  | той самий алгоритм і коміт, конфіг stereo — база для порівняння |
| `run-0207`, `run-0208` | OpenVINS на EuRoC                                               |
| `run-0209`             | OpenVINS, зрив трекінгу на 47.3 с → метрик не існує             |
| `run-0231`, `run-0232` | OpenVINS на TUM-VI                                              |
| `run-0288`             | DROID-SLAM, власний датасет без ground truth, лога немає        |

`run_id` навмисно **непрозорий**. Старий формат (`run-2026-07-12-orb3-euroc-si`)
модель могла сконструювати з голови, знаючи алгоритм і дату. З `run-0141` це
неможливо — правило «`run_id` береться з інструмента» стало фізичним обмеженням,
а не побажанням в описі.

## Інструменти й ціна префікса

П'ять інструментів на М1. Виміряно через `messages.count_tokens`:

| інструмент                      | токенів у префіксі |
| ------------------------------- | ------------------ |
| `scan_log`                      | 318                |
| `find_runs`                     | 309                |
| `search_logs`                   | 259                |
| `get_metrics`                   | 185                |
| `get_run`                       | 184                |
| **разом із системним промптом** | **1868**           |

Ціна не в кількості інструментів, а **в прозі описів**. Найдорожчі — ті, чиї описи
несуть попередження («підрахунок робить бекенд», «`run_id` конструювати не можна»).
Ці абзаци купують правильну поведінку, і вони ж і є витрата.

## Шар знань (RAG)

`domain/knowledge.py` — 16 правил команди: пороги прийняття, методика вирівнювання,
валідність прогонів, діагностика, політика повторів. Це **не дані про прогони** —
ті в `backend.py`. Тут те, чого модель не знає з ваг і що не порахувати з логів.

Підключення — один доданок у системний промпт (`modules/m02_rag.py`):

```python
system=BASE_PROMPT + as_context(query)
```

### Ембединги проти лексики

`domain/knowledge_vec.py` — `intfloat/multilingual-e5-small`, косинус, поріг **0.78**.
Інтерфейс той самий (`retrieve` / `as_context`), тож модуль про заміну не знає.

| запит | лексика | вектор |
|---|---|---|
| «Система розвалилась посеред прогону» | 0 правил | **0.795** → Правило 3.2 («зрив трекінгу») |
| «Стерео краще за інерціалку, вимикаємо IMU?» | 0 правил | **0.861** → Правило 1.5 |

Клієнт каже «розвалилась», у правилі — «зрив трекінгу». Спільних слів нема,
префіксне порівняння безсиле.

Поріг тюниться на своїх даних, а не береться з підручника: `0.795` правильне
правило, `0.764` нерелевантне — між ними **31 тисячна**, і поріг проходить рівно там.
Дивитись розкид: `knowledge_vec.scores(query)`.

### Чесна відмова

`retrieve` **fail-closed**: нижче порога — порожньо, а не «найменш нерелевантне».
Хибне правило про поріг заблокує коректний мердж; порожній контекст лише зробить
відповідь загальнішою.

| запит | retrieved | відповідь |
|---|---|---|
| «Скільки коштує година на кластері?» | 0 | «поза межами моєї компетенції» |
| «Яка у нас політика зберігання бегів?» | 0 | відмова, перелік того, що вміє |
| «Який у нас поріг ATE для монокулярних?» | 3 | «пороги задані Правилом 1.2 і залежать від складності, не від конфігурації» |
| «Яка допустима частка кадрів із low_features?» | 3 | «прямого порогу в базі немає», далі суміжне Правило 3.1 |
| «Скільки прогонів для стабільної регресії?» | 3 | «Правило 1.3 цього не встановлює» |

Найважчі — три останні: питання **в домені**, звучать так, ніби норма мала б бути,
але її немає. Агент знаходить суміжні правила й прямо каже, що прямої відповіді
в базі нема — замість добудувати правдоподібне число. 5 із 5 без вигадок.

### Що видно понад завдання

**RAG не прибирає галюцинацію, а переміщує її.** На М1 агент вигадував кількість
фіч для ініціалізації — три прогони давали «20–50», «від 20», «50–150». На М2 —
«щонайменше 80» з посиланням на Правило 3.1, тричі однаково. Але коли ретрив
промахується, агент однаково відповідає з ваг — тепер із авторитетом системи,
яка зазвичай цитує.

**Наївний RAG не дістає правило, про яке користувач не знає.** Запит «хто точніший:
ORB-SLAM3 на MH_01_easy чи OpenVINS на room1?» — це порівняння між датасетами,
заборонене Правилом 2.2. Ретрив дав **0**: у запиті названі сиквенси, у правилі —
датасети. Ембединги це теж не лагодять: зв'язок `MH_01_easy → EuRoC` це факт із
бази, а не семантична близькість. Такі правила треба або підмішувати кодом за
умовою, або питати KB **після** інструментів, коли `dataset` уже відомий.

**KB працює ще й як сигнал про домен.** На запиті «Що у нас з EuRoC датасетами?»
М1 у 3 з 3 прогонів відповідав із ваг про публічний бенчмарк, не торкаючись даних.
М2 у 3 з 3 йшов у `find_runs`. У відповідь не потрапило жодного правила — вони лише
переключили прочитання «EuRoC» з енциклопедії на наш реєстр.

### Чанкінг

`chunking.py --compare` — розбиття внутрішньої методички (221 токен) на різних
розмірах, три пари фактів, які мають лишатись разом.

```
   25 ток. · перетин  0 →  9 чанків   A РВЕТЬСЯ   B РВЕТЬСЯ   C разом
   60 ток. · перетин  0 →  4 чанків   A разом     B РВЕТЬСЯ   C разом
   60 ток. · перетин 18 →  5 чанків   A РВЕТЬСЯ   B РВЕТЬСЯ   C разом
  120 ток. · перетин  0 →  2 чанків   A разом     B разом     C разом
```

**Перетин не замінює достатній розмір чанка.** На 60 токенах він не полагодив,
а зламав пару A: overlap зсуває всі межі, тож факти, що випадково вміщались
в один чанк, опиняються на межі. Пара A рознесена на ~40 слів (пункти 3.2 і 3.3),
чанк 60 токенів ≈ 46 слів — на грані. Надійно тримає лише 120.

Спершу розмір має перекривати відстань між повʼязаними фактами, і тільки потім
перетин добирає крайові випадки.

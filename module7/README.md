# Модуль 7 — Observability та Evaluation

Продовження модуля 6. **Додається:** eval-датасет + гейт замість ручної
перевірки — і найсильніший момент курсу: тиха деградація.

## Нове відносно модуля 6

- `modules/m07_evaluation.py` — 14 кейсів по 5 долях посилок; на кожен дві
  незалежні перевірки: чи викликано правильний інструмент (детерміновано,
  безкоштовно) і LLM-judge за критерієм (дешева модель, temperature=0,
  суддя бачить УСЮ базу правил). Гейт: 0.8.
- `data/evalset.json` — сам датасет.
- `degradation_demo.py` — агент не змінювався, «вийшов реліз API v2»
  бекенду (дні від останнього сканування, статуси перекодовано). Логи
  чисті, відповіді впевнені — гейт падає: 14/14 → 10/14 на живому прогоні.
- `eval_history.py` — «до/після» у `out/eval_history.jsonl`: скор сам по
  собі не значить нічого, значить дельта.
- `langfuse_tracer.py` — той самий Tracer, спани їдуть у Langfuse
  (без ключів деградує до локального).

## Запуск

```bash
python run.py 7                     # eval + гейт
python eval_history.py baseline     # записати прогін
python degradation_demo.py          # зірка курсу (~2×28 LLM-викликів)
python eval_history.py --compare
```

## Історія, яку варто розповісти групі

Важіль деградації шукали чотири рази: вимкнений retrieval, викинуті
тексти правил і «інструменти дорогі, викликай рідше» деградації НЕ дали —
політика продубльована в типізованих полях бекенду, а суддя без
temperature=0 хитав гейт (одного разу «деградований» прогін обігнав
здоровий). Спрацював лише дрейф даних — найчесніший продакшн-сценарій.
Мораль: eval ловить деградацію ДАНИХ, не лише промптів → online-евали.

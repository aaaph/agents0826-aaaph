# Модуль 2 — RAG / Agentic RAG

Продовження модуля 1. **Додається:** база правил і тарифів у контексті —
агент починає цитувати «Правило 4.2» замість вигадувати.

## Нове відносно модуля 1

- `domain/knowledge.py` — база правил + наївний лексичний retriever
  (навмисно без векторної БД — щоб було що ламати).
- `modules/m02_rag.py` — правила підмішуються в системний промпт.
- `chunking.py` — чанкінг наочно: розмір, перетин, і на яких розмірах
  пов'язані факти рвуться між чанками.
- `knowledge_vec.py` — векторний retriever з тим самим інтерфейсом
  (локальна multilingual-e5-small або OpenAI — обирається сам).
- `knowledge_qdrant.py` — той самий retriever у векторній БД: payload,
  фільтри по метаданих, `score_threshold` замість повного перебору.
- `self_rag.py` — ворота перед відповіддю (Self-RAG / CRAG): поріг →
  LLM-grade → переформулювання → ескалація, якщо правила таки немає.
- `rag_agentic.py` — retrieval як інструмент `search_kb`: агент сам
  вирішує, коли і що шукати.
- `ragas_compare.py` — агент з 3 RAG-конфігураціями (lexical / vector /
  agentic) під метриками Ragas; головна — context_recall.

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python run.py 1 2              # порівняти відповіді М1 і М2 поруч
python chunking.py --compare   # розмір і перетин чанка (офлайн)
python knowledge_vec.py        # де ламається лексика (частина 1 — офлайн)
python knowledge_qdrant.py     # те саме у векторній БД (без Docker, :memory:)
python self_rag.py             # ворота: grade → rewrite → ескалація
python rag_agentic.py          # static проти agentic
pip install -r requirements-eval.txt   # важкий стек, лише для наступної команди
python ragas_compare.py        # 3 конфігурації під Ragas (~хвилини)
```

## Qdrant: сховище змінилось, агент — ні

```bash
python knowledge_qdrant.py            # вбудований режим, нуль інфраструктури
python knowledge_qdrant.py --filter   # пошук лише серед правил про компенсацію

docker run -p 6333:6333 qdrant/qdrant                       # справжній сервер
QDRANT_URL=http://localhost:6333 python knowledge_qdrant.py
```

Контракт `retrieve()` / `as_context()` той самий — **агент про заміну
сховища не дізнається**. Що зʼявляється порівняно зі списком у памʼяті:
окреме сховище (індекс переживає рестарт), payload з метаданими поруч із
вектором, фільтри + ANN-пошук, і `score_threshold` — той самий fail-closed,
але вже на рівні БД.

## Нюанси заняття

- Пастка в `retrieve()`: якщо нічого не знайшлось — повертає найменш
  нерелевантне правило (fail-open). У `knowledge_vec.py` — fail-closed.
  Спитайте групу, який варіант гірший.
- Поріг вектора (`_THRESHOLD`) тюниться на даних: `scores()` друкує
  косинуси — на живому прогоні правильне правило і хибне розділяло 0.013.
- RAG ≠ пам'ять: правила — «як заведено», пам'ять — «що ми вже з'ясували».

**Далі (модуль 3):** агент розумний, але смертний — убийте процес посеред
діалогу, і все почнеться спочатку.

## Чанкінг: чому в нашій KB його немає

У нас одне правило = один чанк (~40 токенів), бо правила вже нарізані
людиною. `chunking.py` показує, що буває, коли джерело — суцільний
документ (PDF умов, стаття, транскрипт):

```bash
python chunking.py            # розбиття з підсвіткою перетину
python chunking.py --compare  # де саме рвуться пов'язані факти
```

Ключовий рядок таблиці — **60 токенів**: без перетину сума «120 грн»
опиняється в одному чанку, а умова «5 і більше днів» — у сусідньому,
і агент бачить лише половину правила. З перетином 18 токенів обидва
факти тримаються разом. Це і є відповідь на питання «навіщо overlap».

25 токенів не рятує навіть перетин — чанк менший за саме правило;
120 тримає все, але тягне в промпт цілий розділ.

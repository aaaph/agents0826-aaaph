# Модуль 6 — Безпека агентів і Guardrails

Продовження модуля 5. **Додається:** вихідний guardrail (перевірка
відповіді ПЕРЕД показом) + детерміновані PreToolUse-хуки + живі атаки.

У чат-бота поганий вихід — поганий текст. У агента — погана ДІЯ.

## Нове відносно модуля 5

- `modules/m06_security.py` — трейсинг кроків + guardrail на дешевій
  моделі: `{pii_leak, unsupported_promise, verdict: pass|block}`.
- `hooks.py` — deny-правила перед `dispatch()`: claim без валідного
  трек-номера, ліміт претензій за сесію. Модель помиляється — код ні.
- `attacks.py` — дві атаки: injection у даних (отруєне відправлення
  `EE666000666UA`, інструкція в полі `last_scan` — смертельна трійця
  в зборі) і PII («продиктуйте номер картки з бази»).
- `evalset_attacks.json` — кейси атак для eval (стануть у пригоді на М7).

## Запуск

```bash
python hooks.py       # офлайн: deny-правила, без ключа
python run.py 6
python attacks.py     # обидві атаки наживо
```

## Чотири шари захисту (зібрати на дошці)

вхідний фільтр → PreToolUse-хуки → CAPABILITIES-allowlist (він у проєкті
з М1!) → вихідний guardrail. Мінімум для проду — 2–3.

## Нюанси з живих прогонів

- Модель нерідко нейтралізує injection САМА — `attacks.py` чесно друкує,
  який шар спрацював. На дисциплінованість моделі не закладаються.
- Наш guardrail fail-open (нерозпарсений JSON → pass). Fail-closed теж
  болить — легітимні відповіді летять в оператора. Це вибір, не баг.
- Ескалація `no_tool_used` може перебити коректну відмову — ціна
  консервативної політики, обговоріть.
